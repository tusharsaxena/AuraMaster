# Automated test records

Every run of the four out-of-game suites, recorded (automated-tests). This file is the local how-to;
the normative rules are the standard's `automated-tests` section.

## Running

From the repo root:

```sh
tests/_kit/run-automated-tests.sh                                          # all four suites, writes a bundle
tests/_kit/run-automated-tests.sh --suite complexity                       # a subset, still recorded
tests/_kit/run-automated-tests.sh --suite lint --suite tests --no-bundle   # the green gate; writes nothing
tests/_kit/run-automated-tests.sh --release 0.1.0                          # the release record for v0.1.0
```

`--release` marks the bundle as the evidence for that version, and the runner **refuses it on a dirty
working tree** (exit 2, before any suite runs): commit first, then run, then commit the record. A
release run needs an `ANALYSIS.md` in the bundle, written in the same change that bumps the version and
before the tag (automated-tests-§5/§6).

The runner is **vendored** from LibKa0s's `testkit/` and byte-identical in every Ka0s addon; it is a
bash script and must stay LF (`.gitattributes` carries `*.sh text eol=lf`). Never edit it here — a fix
goes upstream and arrives on the next re-vendor (automated-tests-§2).

## What a bundle holds

```
docs/automated-tests/<YYYYMMDD-HHMMSS>/     local time
  manifest.json      every suite's status and counts, the version, the git sha, the gates object
  ANALYSIS.md        the write-up (required on a release run)
  lint.txt           luacheck output
  tests.txt          harness output
  test-cases.md      the generated inventory as it stood for this run
  perf.txt           tests/perf.lua output, and perf.json, its record
  complexity.txt     raw lizard output
```

Bundles are **frozen once written** and never pruned; a wrong reading is corrected by the next run's
analysis, never by editing an old one.

`RESULTS.md` beside this file is the trend line: one row per run across all four suites, overwritten
in place so its git history is the comparison, plus the complexity watch list and a standing section
per suite. It is **generated by the runner**. The one authored cell is the watch list's `Disposition`
column, which the runner carries forward while its entry is unchanged (automated-tests-§4).

## What gates, and what only records

There are **two checkpoints**, and a suite's answer differs between them:

| Suite | Command | Run + commit | Release tag |
|---|---|---|---|
| `lint` | `luacheck .` | **gates** | **gates** |
| `tests` | `lua tests/run.lua` | **gates** | **gates** |
| `perf` | `lua tests/perf.lua` | does not gate — recorded | **gates** — `pass` required |
| `complexity` | `lizard -l lua -x "./libs/*" -x "./tests/_kit/*" .` | does not gate — recorded | **gates** — `pass`, zero functions above CCN 15 |

**The run and the commit.** `lint` and `tests` are the green gate (testing-§4). `perf` and
`complexity` never fail a run and never block a commit (performance-§9, performance-§10): they are
measured, recorded and diffed, and contribute `amber` at worst. A missing tool is recorded as a
**skip with its reason**, never as a pass or a failure. Verdicts: `red` — a gating suite failed;
`amber` — a gating suite was skipped, or `perf` failed its own deterministic assertions; `green` —
gating suites passed and nothing went unmeasured without saying so.

**The release tag** (automated-tests-§3, *The release gate*). No version is bumped, no
`## Version History` rolled and no tag cut unless the release run's `manifest.json` shows **all four**
suites at `pass` and `suites.complexity.warnings` at `0` — no function above CCN 15. A **skip** there
is **not evaluated**, so it does not pass: install the tool and run again. The one narrow exception is
a `perf` skip because an addon ships no `tests/perf.lua`, which must be stated in the release notes;
this addon ships one. The gate is evaluated by the release command reading the manifest, not by the
runner, whose exit code stays the commit gate's. Every failed gate is reported, not the first, and a
failed gate means nothing is bumped, tagged or pushed.

In-game captures are a different store: [`../perf-analysis/`](../perf-analysis/README.md).
